# ashokify: MVP scope and deployment audit

Current workflow: Ashokify generates deployment files once and keeps no saved answers or tracking manifest. Configuration persistence and regeneration sections below describe the earlier design; [IMPLEMENTATION.md](IMPLEMENTATION.md) and [../README.md](../README.md) describe the current behavior.

Audit date: 7 September 2026.

Ashokify helps developers prepare a frontend repository for deployment through Azure DevOps. The first release generates and validates repository configuration; later stages handle hosts, service connections, secure files and pipeline execution.

This document records the proposed scope and the read-only audit. No cloud resources, service connections, permissions, boards or pipeline runs were changed. The Docker setup script was inspected but not executed.

## Release scope

### Local repository preparation

Check Git, confirm the stack, collect settings, preview changes, generate files, validate them and offer one commit. Azure authentication is unnecessary for this stage.

### Run the deployment setup

Connect Azure DevOps, reuse or provision a host, configure authenticated Docker access, create or reuse connections, upload files, authorize the pipeline and offer to run it.

Keep **pipeline provider**, **container registry** and **hosting provider** as separate settings. Azure DevOps can use Azure Container Registry and deploy to AWS EC2. AWS remains disabled in the initial provider prompt; EC2 provisioning is also outside the MVP.

## The MVP prompt sequence

The first supported deployment recipe is a Vite static frontend, regardless of whether it uses React, Vue or another UI framework. Build the application's static output; let the developer choose how it is served. Do not generate `nginx.conf` or add Nginx images, installation steps or configuration to Dockerfiles by default. Vite applications that require a server at runtime need a separate recipe and remain outside the MVP.

## Reuse shadcn's detection with clear limits

The [project detector](https://github.com/shadcn-ui/ui/blob/main/packages/shadcn/src/utils/get-project-info.ts) reads configuration files and dependencies to identify Next.js, Vite, Astro, Remix, React Router and other frontend-oriented setups. It also gathers TypeScript, Tailwind and alias details. Ashokify does not need to distinguish React from Vue for static Vite deployment. It needs the build command, package manager, output directory and confirmation that the output can be served as static files.

The public [shadcn info command](https://ui.shadcn.com/docs/cli#info) supports JSON output. The inspected [utils exports](https://github.com/shadcn-ui/ui/blob/main/packages/shadcn/src/utils/index.ts) do not expose the detector as a library function. The info command also collects component and registry information, which adds work unrelated to deployment.

**Proposed implementation:** adapt the narrow framework-detection portion at a pinned upstream revision, preserve its MIT notice and attribution, and place it behind an ashokify detection interface. Add checks for scripts, lockfiles, Node engine requirements, static output and application location. This reuses existing detection logic without importing private package paths. Calling a pinned `shadcn info --json` is an available integration path if direct CLI reuse is preferred.

The Node version applies to the Docker build stage. The developer's serving choice determines the final image or artifact destination; no web server is assumed. The [`engines.node` field](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#engines) declares Node compatibility and can contain a version range; it does not indicate whether an application requires a running server. [Vite supports both static deployment and SSR](https://vite.dev/guide/static-deploy), so the MVP must identify or confirm static output and reject known server-dependent builds. No React/Vue-specific deployment checks are needed.

Report evidence for the detection and keep confirmation editable. Do not install dependencies or execute application configuration files just to identify the stack. Custom or unsupported builds should fail before writing files.

## Files and repeatability

### Generated or updated

- `azure-pipelines.yml`
- `Dockerfile` using the confirmed build and serving choices, with no Nginx-specific content by default
- `docker-compose.yml` and `docker-compose.override.yml`
- `.dockerignore` and `.gitignore`
- `.env.example` and one public `.env.build.<environment>` per selected environment
- `ashokify.config.json` containing nonsecret answers and template version
- `DEPLOYMENT.md` with resource names and remaining setup steps

Generate `nginx.conf` and Nginx-specific Dockerfile content only when the developer explicitly chooses Nginx and requests configuration for it. Preserve existing Nginx and serving configuration belonging to other projects, along with any shared host proxy configuration. If serving is deferred, record it as an outstanding deployment requirement; do not describe a build-only image as a running frontend deployment.

### Rules for a safe rerun

- Stable ordering and content, without generated timestamps.
- Merge ignore patterns once, preserve unrelated rules.
- Detect user edits to managed files and show conflicts.
- Never silently remove lint or other existing quality gates.
- Catch hook or Git identity failures and retain the generated changes.
- Do not stage unrelated files created while prompts were open.
- Validate using temporary copies so build output does not enter the commit.

One optional commit is the delivery unit. Idempotency is a separate guarantee: identical inputs generate identical files. If a user declines the commit, the next fresh invocation correctly stops at the dirty-worktree check until the user resolves it.

[Vite bundles exposed variables into browser code](https://vite.dev/guide/env-and-mode). Secure-file storage does not make a `VITE_*` value secret after the build. Keep deployment credentials separate from public frontend configuration and from published release artifacts.

## The full workflow after the MVP

1. **Connect Azure DevOps.** Check executable, extension, authentication, target organization/project and action-specific permission. Distinguish missing tooling, expired credentials, forbidden action, inaccessible resource and network failure. Tell users exactly how to install or sign in and retry. Do not infer write access from a successful list call.
2. **Choose existing or new resources.** Discover and reuse the registry connection and branch host connections where possible. Keep Azure DevOps project, repository, application name and image repository separate. Creating an Azure registry would need Azure subscription access in addition to DevOps access.
3. **Prepare the host.** Support an existing host, then AWS EC2 provisioning later. EC2 questions cover AWS account/profile, region, name, instance type/CPU architecture, Ubuntu image, disk, VPC/subnet, security group, access method and network reachability. Show the concrete resource plan and obtain consent before creating a billable resource. Azure login alone cannot provision EC2.
4. **Bootstrap and verify Docker access.** Install the engine/plugins, configure authenticated access, network/firewall rules and any required VPN, then verify reachability from the deployment agent. Match image architecture to the machine. Configure ingress and TLS/domain separately when needed.
5. **Create or reuse connections.** Registry access and remote Docker access are distinct resources. For a newly provisioned host, finish the host before creating its connection because the endpoint and credentials must exist. The CLI may collect this choice earlier, but execution must follow that dependency.
6. **Upload selected secure files.** Ask for an environment and local path, validate the file, show the destination name without printing contents, and upload only after confirmation. Detect duplicate names and make replacement explicit. Include VPN material only when the chosen networking method requires it.
7. **Register and authorize the pipeline.** Create or reuse the Azure pipeline definition pointing to the committed YAML. Authorize the specific pipeline for its service connections, secure files and required agent pool. A YAML file in Git does not complete these external setup steps.
8. **Offer to run.** Confirm the remote branch and revision contain the generated files. If only local, explain the required push or offer it separately. Resource creation should not silently queue a run. Then ask to run on a selected branch, show the result URL and report failures by stage.

Each stage needs a resumable record of nonsecret resource IDs and completion status. Retrying should discover existing resources, avoid duplicate instances or connections, and continue after a failure. Skipping a prerequisite must leave downstream execution blocked with a useful explanation.

Microsoft documents [Docker-host certificate fields and pipeline connection authorization](https://learn.microsoft.com/en-us/azure/devops/pipelines/library/service-endpoints?view=azure-devops#docker-host-service-connection), [CLI service-endpoint creation](https://learn.microsoft.com/en-us/cli/azure/devops/service-endpoint?view=azure-cli-latest), and [secure-file permissions](https://learn.microsoft.com/en-us/azure/devops/pipelines/library/secure-files?view=azure-devops). Uploading a file or creating a connection alone does not grant a YAML pipeline permission to use it.

## The supplied Docker script covers installation only

`/home/mohiwalla/Downloads/Helper Scripts/install-docker.sh` removes conflicting packages, installs Docker's Ubuntu apt repository, then installs the Docker engine, CLI, containerd, Buildx and Compose plugin. It does not create a context, configure a TLS listener, generate certificates, install Tailscale, configure ingress, or create application networks.

The observed Azure Docker-host connection uses certificate authentication. [Docker supports authenticated access over SSH or TLS](https://docs.docker.com/engine/security/protect-access/); the connection recipe must match the pipeline task. A developer's local Docker context alone does not configure the hosted pipeline agent. A future bootstrap should validate its supported Ubuntu release, stop on failures and verify the completed setup. This audit does not establish Ashok's missing certificate/bootstrap steps.

## What makes the MVP complete

- Run from the published npm package using `npx ashokify`. Develop and test with Bun, but ship a Node-compatible executable so users do not need Bun installed.
- Exercise successful detection, unknown stack, manual correction and unsupported selection without writing premature files.
- Verify custom branch mapping across triggers, environment files, image identifiers and service-connection references.
- Parse generated YAML, validate Compose with representative nonsecret variables, and build a supported frontend fixture in Docker.
- Verify the default generated files contain no Nginx configuration or Dockerfile instructions. Verify serving, SPA route fallback and proxy behavior only for the developer-selected setup.
- Verify independent projects can coexist on a shared EC2 host with distinct service names and configured ports/networks, without overwriting another project's Nginx setup or shared host proxy configuration.
- Prove dirty-worktree rejection, cancel behavior, exact commit contents, declined commit, conflicting existing files and unchanged reruns.
- Keep private overrides ignored, exclude them from Docker context, and keep deployment credentials out of browser build arguments and release artifacts.

No CLI implementation or deployment tests were run during this audit. Template architecture, host bootstrap details and broader framework support remain implementation work.
